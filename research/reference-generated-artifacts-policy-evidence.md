# Generated-artifacts zone — OKF evidence and policy constraints

> Evidence for Wayfinder ticket [#36](https://github.com/artemVeduta/skills/issues/36),
> “Generated-artifacts zone: what belongs in the bundle.” Researched 2026-07-22
> against Google’s OKF v0.1 specification and reference implementation at commit
> [`d44368c`](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/d44368c15e38e7c92481c5992e4f9b5b421a801d/okf),
> plus this repository’s committed benchmark-artifact decision. This note supplies
> evidence and constraints; it deliberately does **not** choose the HITL policy.

## Executive findings

1. **Generation is not a reason to exclude content from OKF.** OKF is expressly
   designed for knowledge authored by people or generated by agents, and Google’s
   reference agent generates conformant concept documents and indexes. The relevant
   distinction is therefore *knowledge concept versus operational output*, not
   hand-written versus generated. [Spec introduction and goals][spec-intro]
   [Google Cloud announcement][google-blog]
2. **The bundle boundary is decisive for Markdown.** A bundle is a directory tree of
   Markdown files; `index.md` and `log.md` are the only reserved filenames, and every
   other `.md` file anywhere in that tree is a concept document. Conformance requires
   every such document to have parseable frontmatter with non-empty `type`.
   [Spec §§3, 3.1, 9][spec]
3. **OKF v0.1 defines no excluded directory, generated-artifact directory, file-size
   limit, duplicate rule, retention rule, or archive convention.** Directory structure
   is producer-chosen and domain-independent. Consequently, any `runs/`, `archive/`,
   or ignored-prefix semantics would be this suite’s producer-side convention, not an
   OKF rule. [Spec §3][spec-structure]
4. **Non-Markdown sidecars are outside the specified concept/conformance surface.**
   The conformance algorithm speaks only about `.md`; it neither validates nor assigns
   concept identity to JSON, HTML, images, PDFs, or binaries. Google nevertheless
   publishes a generated `viz.html` next to each sample bundle and makes
   `<bundle>/viz.html` the viewer’s default output, demonstrating first-party
   coexistence rather than a normative extension of OKF. [Spec §§2, 3, 9][spec]
   [Reference CLI][cli] [Reference README][readme] [GA4 sample bundle][ga4-bundle]
5. **A consumer cannot be assumed to understand producer-local artifact semantics.**
   OKF standardizes paths as concept identity and reserves only two filenames. It
   deliberately separates producers from consumers and requires tolerance for unknown
   types, extra frontmatter keys, broken links, and missing indexes; none of that gives
   an exclusion directory portable meaning. [Spec §§2, 4.1, 9][spec]
   [Google Cloud announcement][google-blog]
6. **This repo already has a useful retention precedent, but it is not an OKF rule.**
   Benchmark runs keep raw transcripts and fixture state in git-ignored `tools/runs/`,
   while committing compact summary JSON and deterministic Markdown reports under
   `tools/benchmarks/`. The rationale is bounded repository growth, publication-risk
   reduction for transcripts, shared provenance, and regeneration from committed
   summaries. [Local decision][local-decision] [Local artifact reference][local-reference]

## What the normative OKF contract does and does not cover

### Bundle membership and reserved names

- A knowledge bundle is the unit of distribution and is a self-contained,
  hierarchical collection of knowledge documents. A concept is exactly one Markdown
  document; its ID is its path under the bundle root without `.md`.
  [Spec §2][spec-terminology]
- The producer may choose any directory hierarchy. There are no reserved directory
  names. At every level, only `index.md` and `log.md` have reserved meanings; all other
  `.md` files are concepts. [Spec §§3–3.1][spec-structure]
- A conformant bundle must validate every non-reserved `.md` in the tree. Thus an
  “excluded” subtree **inside the declared bundle root does not remove generated
  Markdown from OKF’s normative scope**. A producer-local validator may skip it, but
  the resulting whole tree cannot be claimed conformant under §9 unless those Markdown
  files are themselves conformant concepts. [Spec §9][spec-conformance]
- Conversely, §9 has no requirement for other extensions. This is best described as
  spec silence: it is evidence that non-Markdown sidecars do not participate in OKF
  concept conformance, not a promise that every consumer will preserve, copy, render,
  index, or serve them. [Spec §9][spec-conformance]

### Consumer tolerance is narrow and explicit

Consumers must not reject a bundle because optional fields are absent, types or extra
frontmatter keys are unknown, cross-links are broken, or indexes are missing. This
permissiveness supports gradual and partially agent-generated bundles. The list does
not define unknown *paths* as ignorable namespaces: a `.md` at an unknown path is still
a concept because identity is positional and hierarchy is producer-defined.
[Spec §§3, 4.1, 9][spec]

Producer-side strictness remains possible. Google’s own writer requires `type`,
`title`, `description`, and `timestamp` before it will write, even though OKF itself
requires only `type`. This is direct first-party precedent for stricter authoring
conventions that do not redefine the consumer interoperability floor.
[Reference document model][document-model] [Reference write tool][write-tool]

### Links and references to artifacts

- OKF concept relationships use ordinary Markdown links to other concept documents;
  bundle-root-absolute and relative `.md` forms are specified. Relationship semantics
  live in surrounding prose, and broken concept links remain valid input.
  [Spec §5][spec-links]
- External support belongs in `# Citations`; citation targets may be external URLs,
  bundle-relative paths, or paths to `references/` concepts. The optional `resource`
  field is a canonical URI for the underlying asset described by a concept.
  [Spec §§4.1, 8][spec-citations]
- The spec does not define a special relationship type or portability guarantee for a
  link to local JSON, HTML, an image, a PDF, or a binary. Such a link remains ordinary
  Markdown, while a stable external artifact can be represented by a concept whose
  `resource` is its canonical URI. A policy should therefore distinguish “valid
  Markdown link” from “portable OKF concept relationship.” [Spec §§4.1, 5, 8][spec]

## First-party implementation behavior (informative, not normative)

Google labels both the reference agent and viewer proofs of concept; the format, not
their exact behavior, is the contract. Their behavior is still useful interoperability
evidence. [Reference README][readme]

| Concern | Observed behavior | Constraint on local policy |
|---|---|---|
| Consumer scan | The viewer recursively scans `*.md`, skips `index.md`, silently skips parse errors, and does not read non-Markdown files. It serializes every accepted concept body into one HTML payload. [Viewer generator][viewer-generator] | A large conformant Markdown archive may be accepted but can directly inflate consumer work and generated output; OKF provides no size backstop. |
| Reserved files | The viewer explicitly skips `index.md`; it does not explicitly name `log.md`, although a conventional frontmatter-free log is parsed with no `type` and displayed as `Unknown` by this implementation. [Viewer generator][viewer-generator] | Do not infer full spec enforcement from the sample consumer. A local validator must use the spec, not mirror this omission. |
| Unknown/non-Markdown files | Index regeneration discovers directories from `*.md`, indexes only child `.md` files and child directories, and ignores other child files. [Index generator][index-generator] | JSON/HTML/image sidecars are invisible to this producer’s progressive-disclosure index. If humans or tools must discover them, a concept or other explicit producer convention is required. |
| Generated viewer placement | `visualize` defaults to `<bundle>/viz.html`; Google commits that file alongside each sample bundle and documents committing or hosting it. [Reference CLI][cli] [Reference README][readme] | A non-Markdown generated sidecar can coexist with a bundle in first-party practice, but this does not make it an OKF concept or require other consumers to carry it. |
| Links | Graph extraction recognizes relative `.md` targets and drops edges whose target concept is missing; browser-side rewriting recognizes bundle-root-absolute `.md` links. Non-`.md` links receive no OKF graph behavior. [Viewer generator][viewer-generator] [Viewer JavaScript][viewer-js] | Artifact links should not depend on graph navigation or special consumer treatment unless the target is represented by a concept. |
| Producer output | The agent writes/overwrites UTF-8 Markdown concepts, then regenerates `index.md` files. Its writer refuses documents missing its producer-required metadata. [Runner][runner] [Reference write tool][write-tool] | Generated durable knowledge can remain inside the bundle when emitted as proper concepts with stable identity and lifecycle. |

Two implementation caveats matter when interpreting the table: the viewer excludes
only `index.md` even though the spec reserves `log.md`, and its edge extractor ignores
bundle-root-absolute links even though §5 recommends them. These mismatches reinforce
that first-party tool behavior is evidence about likely consumers, not a substitute for
the normative specification. [Viewer generator][viewer-generator] [Spec §§3.1, 5][spec]

## Local committed-artifact precedent

The repository’s benchmark decision separates outputs by durability and disclosure
risk rather than by extension:

- raw transcripts, resulting fixture state, and per-assertion results remain local and
  git-ignored under `tools/runs/`;
- compact summary JSON is committed as shared provenance-bearing truth;
- a deterministic Markdown report is committed but regenerable from that summary;
- the decision rejected committing raw artifacts because of repository growth and the
  chance that transcripts expose environment details.

This precedent lives outside `docs/`, so neither committed reports nor summaries are
mistaken for OKF concepts. The docs bundle contains one durable `Reference` concept
that explains where the artifacts live and links to the governing `Decision`.
[Local decision][local-decision] [Local artifact reference][local-reference]

This precedent supports evaluation dimensions—shared truth, reproducibility,
regenerability, volume, and sensitivity—but does not settle whether ticket #36 should
use the same layout for every artifact family.

## Policy constraints for the HITL decision

The eventual policy should preserve all of these constraints:

1. **Declare one unambiguous bundle root.** Whether a path is inside that root changes
   the conformance status of every generated `.md` beneath it.
2. **Do not call a skipped Markdown subtree OKF-conformant by exclusion alone.** Choose
   either: put it outside the bundle; emit every retained Markdown file as a conformant
   concept; or explicitly describe the whole tree as mixed/nonconformant rather than
   weakening §9 invisibly.
3. **Treat any artifact-zone name as a house convention.** `runs/`, `archive/`, hidden
   directories, or glob exclusions have no portable meaning in OKF v0.1 and need local
   wiring for producers, validators, indexes, packaging, and consumers.
4. **Keep validator severity separate from consumer acceptance.** Size, duplicate,
   retention, sensitivity, and regenerability findings can be producer-side advisory or
   strict checks, but none is an OKF conformance error unless the Markdown/reserved-file
   rules fail.
5. **Specify discovery and reference behavior.** Ordinary links to non-Markdown assets
   may work in a repository browser yet be absent from OKF indexes, graph viewers,
   archives, or downstream ingestion. Define whether a durable summary/reference
   concept, canonical `resource` URI, or both are required.
6. **Specify distribution behavior.** Because a bundle may ship alone as a repo,
   archive, or subdirectory, links escaping its root are not self-contained. If raw
   artifacts remain outside, state whether links are repository-local conveniences or
   stable external resources.
7. **Define generated knowledge separately from raw run exhaust.** Deterministically
   generated explanatory material can be a valid concept; voluminous transcripts,
   snapshots, intermediate JSON, duplicate reruns, and binaries have no automatic OKF
   status.
8. **Make any limits explicitly producer-owned.** File-count/byte thresholds,
   duplicate heuristics, ignored extensions, retention windows, and secret scanning
   require local definitions and tests; the spec supplies no portable defaults.

## Questions left for human decision

- Is the canonical artifact zone outside the bundle, a non-Markdown sidecar zone inside
  it, or a concept-producing subtree inside it?
- Which outputs are shared truth worth committing, and which are local/ephemeral due to
  volume, sensitivity, or reproducibility?
- Should the validator merely warn on volume/duplicates, offer an opt-in strict producer
  mode, or leave retention enforcement to a separate tool?
- When a concept refers to a generated output, is a repository-relative ordinary link
  sufficient, or must the output have a stable URI and/or a small describing concept?
- Do bundle packaging/install flows include non-Markdown sidecars, exclude them, or use
  an explicit manifest?
